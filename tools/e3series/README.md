# E3.series — обмен изделиями с Excel

Инструмент: `E3_Devices_Tool.hta` — объединяет прежние два скрипта (экспорт и импорт) в одну
программу и исправляет ошибку с координатами при выгрузке из E3.

Проверялось против **E3.series 2022 SP2, build 23.20.0.0 (64 bit), модуль E3.cable**.

> **Версия на Python** — `python/`, см. `python/README.md`. Та же логика, но код разбит
> на модули, покрыт тестами (включая полный круг «проект → Excel → проект» на поддельной
> E3), Microsoft Excel не требуется, есть выбор экземпляра E3 по PID, консольный режим и
> portable-сборка. Соглашения о вызовах COM там взяты из официальной обёртки Zuken
> (пакет `e3series` на PyPI), а не подобраны перебором. Этот HTA остаётся рабочим и
> ничем не затронут.
>
> Начиная с версии 1.3.0 книга повторяет устройство чертежа: схемная часть и подвал
> ФСА — на отдельных вкладках, вид листа (`.PREFERRED_VIEW`) и формат листа — в
> каждой строке, есть вкладка «Листы» с рамками и видами. Поэтому изделия не
> повторяются в одной таблице, а лист определяется однозначно даже там, где имена
> листов совпадают. Формат листа можно поменять в Excel — при загрузке он
> применится.

## 1. Логика E3: как устроены изделия, листы и размещение

### Объектная модель

E3 — база данных, а не чертёж. Графика вторична, первичны объекты:

```
Job (проект)
├── Sheet (лист)            — страница схемы, имеет имя, формат, рамку
├── Device (изделие)        — логическая единица: клемма, датчик, реле, шкаф
│   ├── ComponentName       — ссылка на компонент в библиотеке (БД компонентов)
│   ├── Name                — позиционное обозначение (в API часто с ведущим «-»)
│   ├── Attribute[]         — атрибуты изделия («*TAG титула», «*Контур», ...)
│   ├── Symbol[]            — символы изделия (1..N), графические представления
│   └── Pin[]               — выводы, к ним цепляются соединения
├── Symbol (символ)         — экземпляр символа на листе: лист + точка привязки + поворот
├── Connection / Net / Core — соединения, цепи, жилы
└── Cable                   — кабели (E3.cable)
```

Ключевые следствия, на которых держится вся работа скрипта:

1. **Изделие существует независимо от листа.** `Device.Create` создаёт изделие в проекте;
   его символы при этом существуют, но находятся в состоянии «не размещён» — их нет ни на
   одном листе. Именно поэтому ввод состоит из двух шагов: создать изделие, потом
   разместить символ.
2. **У одного изделия может быть несколько символов** (реле: катушка + контакты; клеммник:
   символ на клемму). Каждый размещается отдельно, на разных листах и в разных координатах.
   Поэтому «координата изделия» — понятие неполное: координата есть у *символа*.
3. **Компонент задаёт набор символов.** Сменить `ComponentName` у существующего изделия
   через API нельзя — изделие пересоздают. Скрипт это только сообщает в лог, сам не делает.
4. **Атрибуты живут на изделии**, а их отображение на листе — отдельные текстовые объекты,
   привязанные к символу. Габарит символа включает эти тексты. Это важно для разбора
   ошибки (раздел 3).
5. **Массивы, которые возвращает API, индексируются с 1**, нулевой элемент не используется
   (в старых скриптах это место было источником сдвигов). Новый инструмент везде обходит
   `LBound..UBound` и пропускает нулевые/отрицательные идентификаторы — база массива больше
   не имеет значения.

### Ввод: из таблицы в проект и на лист

```
строка Excel
   │  Поз. обозначение + ComponentName
   ▼
Job.CreateDeviceObject → Device.Create(поз, "", "", компонент, "", 0)
   │                       изделие создано, символы «не размещены»
   ▼
Device.SetAttributeValues(имена, значения)      ← атрибуты пакетом
   │
   ▼
Device.GetSymbolIds(ids)      → выбираем нужный символ (по ID или по номеру)
   ▼
Symbol.Place(sheetId, x, y)   → символ появляется на листе
   ▼
Job.Save
```

### Вывод: из проекта в таблицу

Два разных обхода, и путать их нельзя:

```
Job.GetAllDeviceIds  → все изделия (в т.ч. неразмещённые) → атрибуты
Job.GetSheetIds → Sheet.GetSymbolIds → Symbol.GetDeviceId → координаты символа
                                                    └── связывает графику с изделием
```

Первый обход даёт «что есть в проекте», второй — «где это лежит».

Инструмент собирает размещения **основным путём от изделий**:
`Device.GetSymbolIds → Symbol.GetSheetId / GetSchemaLocation`. Так номер символа внутри
изделия известен сразу, и результат не зависит от того, отдаёт ли лист список своих
символов. Обход по листам остаётся запасным: он включается, только если путь от изделий
не дал ни одного размещения.

Если размещений нет вообще — это не ошибка выгрузки, а состояние проекта: изделия
созданы (например, прежним импортом), но их символы ещё не поставлены на листы.
В логе это сказано прямо, колонки «Имя листа / X / Y» остаются пустыми.

### Система координат

* Единицы — миллиметры, начало — левый нижний угол листа, Y растёт вверх.
* `Place` принимает **точку привязки символа** (hot point из определения символа
  в библиотеке), а не центр графики и не угол габарита.
* Координаты могут прилипать к активной сетке листа: заданные 100.37 могут стать 100.0.
  Инструмент это обнаруживает — после записи он перечитывает позицию и пишет расхождение
  в лог.

## 2. Что делает новая программа

Один HTA вместо двух, разделы по порядку работы:

| Раздел | Что делает |
|---|---|
| Подключение | `CT.Application` → `CreateJobObject`, кэш листов и изделий, автоподбор сигнатур API |
| Файл Excel | выбор файла, создание шаблона |
| Экспорт | лист «Изделия» (строка на изделие) + лист «Размещения» (строка на символ) |
| Импорт | атрибуты, создание отсутствующих, размещение **и перемещение**, dry-run |
| Диагностика | сравнение всех способов чтения координат; тест «чтение — запись — чтение» |
| Ход работы | живой прогресс, работающая кнопка «Стоп», сохранение лога в файл |

Что изменилось по существу:

* **Координаты читаются точкой привязки символа**, а не габаритом (раздел 3).
* **Размещение работает для существующих изделий.** Прежний импорт для них печатал
  «размещение пропускается»; теперь символ переносится в заданные координаты.
* **Запись проверяется.** После записи координата перечитывается и сравнивается с заданной;
  расхождения попадают в лог и в итоговый счётчик, а не теряются молча.
* **X и Y остаются числами** на всём пути. Прежний экспорт склеивал их в строку
  `лист|X|Y` и разбирал обратно, из-за чего на русской локали в ячейку попадал текст
  «123,45».
* **Столбцы ищутся по заголовку**, а не по жёстким номерам, — можно добавлять свои
  атрибуты и менять порядок колонок. Старый шаблон на 56 колонок продолжает работать.
* **Изделия и листы перебираются от `LBound` до `UBound`** с отбрасыванием нулевых
  идентификаторов: прежний цикл `For i = 0 To count - 1` на 1-based массиве брал пустой
  нулевой элемент и терял последнее изделие.
* **Кнопка «Стоп» действительно останавливает.** В прежних скриптах вызывался `DoEvents`,
  которого в VBScript не существует (это VBA); цикл шёл без обработки событий, и нажать
  «Стоп» было невозможно. Теперь цикл нарезан на порции и прокручивается через
  `window.setTimeout`.
* **Атрибуты пишутся пакетом** `SetAttributeValues`, при отказе — поштучно (как раньше).
* **Excel читается одним куском** (`Range.Value` в массив) вместо обращения к каждой ячейке.

## 3. Почему координаты выгружались неправильно

Причины по убыванию значимости. Первая — основная и объясняет наблюдаемый сдвиг.

### 3.1. Экспорт измерял не ту величину (главное)

Прежний код:

```vbs
symObj.GetArea minX, minY, maxX, maxY
posX = Round((minX + maxX) / 2, 2)   ' центр габарита по X
posY = maxY                          ' верхняя граница габарита
```

`GetArea` возвращает габаритный прямоугольник символа **вместе с его текстами** —
позиционным обозначением, значениями атрибутов, надписями выводов. Центр этого
прямоугольника не связан жёстко с точкой привязки: смещение зависит от типа символа,
от того, куда пользователь оттащил тексты, и от поворота. `Y = maxY` вообще берёт верхнюю
кромку, а привязка у большинства схемных символов внизу или на выводе.

Итог: экспорт отдаёт «где нарисовано пятно», импорт кладёт «точку привязки» — символы
уезжают вверх и в сторону на величину, разную для каждого символа. Ввод при этом работает
идеально, потому что там координаты набиты руками и `Place` их честно исполняет.

Исправление: чтение и запись используют одну величину — позицию символа
(`GetSchemaLocation`, парная к `Place`/`SetSchemaLocation`). `GetArea` остался только
последним резервом и, если дело дойдёт до него, программа явно предупредит в логе.

### 3.2. `IsNumeric(Empty)` = True — проверка не защищала

```vbs
symObj.GetArea minX, minY, maxX, maxY
If Err.Number = 0 And IsNumeric(minX) And IsNumeric(maxX) Then
```

При `On Error Resume Next` неудачный вызов оставляет переменные `Empty`, а `IsNumeric(Empty)`
в VBScript возвращает **True**. Условие проходило, и в файл писались нули или половины
нулей вместо координат. В новом коде есть `IsNum()`, которая отбрасывает `Empty`, `Null`
и пустые строки.

### 3.3. Сдвиг на единицу по массиву изделий

```vbs
deviceCount = ctJob.GetAllDeviceIds(deviceIds)
For i = 0 To deviceCount - 1
    dev.SetId deviceIds(i)
```

Массивы E3 индексируются с 1. Значит `deviceIds(0)` — пустой элемент: первая строка выгрузки
получала `SetId 0` (пустое имя, пустые атрибуты, координаты не находились), а последнее
изделие в файл не попадало вовсе. Сам автор это уже заметил для листов — там стоит
`For sIdx = 1 To sheetCount` с комментарием, — но для изделий цикл остался нулевым.

### 3.4. Одно размещение на изделие, и не то

```vbs
If Not placementMap.Exists(devId) Then placementMap.Add devId, ...
```

Бралось первое встреченное размещение, в порядке обхода листов. Импорт же двигал
`symIds(1)` — первый символ изделия. Для изделий с несколькими символами это разные
объекты, поэтому даже правильная координата уехала бы не тому символу. Теперь экспорт
пишет `ID символа` и номер символа, а лист «Размещения» содержит все символы; импорт
находит ровно тот символ, чья координата записана.

### 3.5. Поворот и зеркало не сохранялись

Повёрнутый символ имеет другой габарит, и `Place` ставит его без поворота. Экспорт теперь
выгружает поворот и зеркало (если сборка отдаёт их через API), импорт применяет поворот.

### 3.6. Числа превращались в текст с локальной запятой

```vbs
placementMap.Add devId, sheetName & "|" & posX & "|" & posY
...
parts = Split(placementMap(deviceId), "|")
dataArray(i, 54) = parts(1)     ' строка!
```

Конкатенация числа через `&` использует системный разделитель дробной части: на русской
Windows получается `"123,45"`. В ячейку попадал текст, формат `0.00` на него не действовал,
а на машине с другой локалью такой файл читается неверно. Теперь по всему пути идут
`Double`, а при чтении из Excel работает разбор, терпимый к обоим разделителям.

### 3.7. Прочее, мешавшее диагностике

* `symObj.GetPosition` в резервной ветке мог не существовать — ошибка гасилась `On Error
  Resume Next`, и координаты становились пустыми без объяснения.
* `For symIdx = 1 To UBound(symIds)` смешивало счётчик и верхнюю границу.
* `lastRow = ws.UsedRange.Rows.Count` в импорте даёт неверную строку, если данные не
  начинаются с первой строки.
* Ошибки нигде не считались: `countError` объявлен и всегда оставался нулём.

## 3b. Опорные факты из официального API

Проверено по типизированной обёртке Zuken над COM-интерфейсом (пакет `e3series` на PyPI,
версия 27) — в ней сохранены оригинальные тексты документации к каждому методу.

| Задача | Как в API на самом деле |
|---|---|
| Позиция символа | `Symbol.GetSchemaLocation(x, y, grid, column, row)`. **Возвращаемое значение — ID листа**, `0` = символ не размещён либо это gate |
| Разместить символ | `Symbol.Place(shti, x, y, rot, scale, maintaintextsize)` |
| Переместить символ | **тот же `Place`**: «Creates and places a symbol item **or moves the current symbol item's position**». Отдельного `SetSchemaLocation` у символа нет — он есть только у `Text` |
| Поворот | `Symbol.GetRotation()` возвращает **строку** («0», «90», «MX90»). Отдельного `SetRotation` нет: поворот задаётся 4-м аргументом `Place`. Зеркалирование закодировано в этой же строке (`MX`, `MY`) |
| Габарит | `Symbol.GetArea` — в **локальной** системе координат символа, а не листа |
| Символ → изделие | **такого метода в API нет вообще**. Ни `GetDeviceId`, ни `GetOwnerDeviceId`; у Symbol есть только сеттеры `SetDeviceName`, `SetDeviceAssignment`, `SetDeviceLocation`. Единственное направление — `Device.GetSymbolIds(get_mode)` |
| Символы изделия | `Device.GetSymbolIds(get_mode)`, где `get_mode` — «Symbol items type filter» |
| Перечисления проекта | `Job.GetAllDeviceIds` (изделия), и **отдельно** `GetTerminalIds`, `GetConnectorIds`, `GetBlockIds`, `GetCableIds`, `GetBusbarIds` |

Последняя строка — причина, по которой символы на листах оставались «ничьими»:
клеммы, разъёмы, блоки и кабели работают через тот же объект `Device`, но в
`GetAllDeviceIds` не входят. Инструмент теперь собирает объекты всеми перечислениями
сразу и строит обратную карту `символ → объект` по ним.

## 3a. Что показала сборка 2022 SP2 на реальном проекте

Диагностика на проекте `13260-14` (71 лист, 230 изделий, 769 символов на листах):

| Метод объекта Symbol | Результат |
|---|---|
| `GetSchemaLocation(x, y, grid)` | **работает**: возвращает ID листа, `x=87, y=42, grid=/2.A2` |
| `GetSchemaLocation(sheet, x, y, grid)` | принимается, но раскладывает значения со сдвигом — не использовать |
| `GetArea(x1, y1, x2, y2)` | работает, но **в локальных координатах символа**: `(0,-21)..(4,0)` |
| `GetDeviceId`, `GetOwnerDeviceId` | ошибка 438 — метода нет (и не должно быть, см. 3b) |
| `GetSheetId`, `IsPlaced`, `GetPosition` | ошибка 438 — методов нет |
| `GetSymbolTypeId`, `GetPinIds` | работают |

На проекте: 71 лист, 230 изделий из `GetAllDeviceIds`, **766 символов на листах**, из них
привязать к изделиям удавалось 0. Символы шли с шагом 4 мм на одной высоте, габарит
4 × 21 мм, по одному выводу — это клеммы. Они и не могли найтись: клеммы возвращает
`Job.GetTerminalIds`, а не `GetAllDeviceIds`.

Два вывода, которые всё объясняют:

1. **Старая формула давала константу.** Раз `GetArea` возвращает габарит в системе самого
   символа, `(minX+maxX)/2` и `maxY` для каждого символа давали одно и то же —
   в этом проекте буквально `X=2, Y=0`. Это не «сдвиг координат», а полное отсутствие
   связи с листом: выгружалось число, не зависящее от того, где символ стоит.
2. **Связь «символ → изделие» через символ недоступна.** Поэтому обход листов сам по себе
   не может сказать, какому изделию принадлежит символ. Инструмент строит **обратную
   карту**: проходит изделия, берёт `Device.GetSymbolIds`, запоминает `символ → изделие`
   и номер символа, и уже потом сопоставляет её с обходом листов.

Ещё две особенности этого проекта, учтённые в инструменте:

* **Перечисление символов изделия зависит от второго аргумента.** `GetSymbolIds(ids, 0)`
  вернул 170 символов на 230 изделий. При подключении инструмент прогоняет варианты
  `GetSymbolIds(ids)`, `(ids,0)`, `(ids,1)`, `(ids,2)`, `(ids,3)`, `(ids,-1)` по первым
  40 изделиям, считает, сколько символов каждый вариант отдаёт и сколько из них реально
  размещено, и выбирает лучший. Таблица подбора пишется в лог.
* **Имена листов не уникальны**: 71 лист на 22 имени («1», «2», «Ведомость_», …).
  Поэтому в экспорт добавлен столбец «ID листа», и при импорте он главнее имени.
  Если в строке задано только имя, инструмент возьмёт первый подходящий лист и напишет
  об этом в лог.

## 3c. Привязка символа к изделию по надписи

Прямой связи «символ → изделие» в API нет (см. 3b), а обратная карта от изделий
покрывает только те символы, которые E3 отдаёт через `Device.GetSymbolIds`. На проекте
13260-14 так нашлось 15 размещений из 243 изделий, тогда как на листах 779 символов.

Поэтому добавлен третий путь: для символа, которого нет в обратной карте, читаются его
надписи (`Symbol.GetTextIds` → `Text.GetText`), и если текст совпадает с обозначением
изделия — символ привязывается к нему.

Сравнение нечувствительно к регистру, пробелам, дефисам, подчёркиваниям и ведущему
минусу: `-094-PDT-1201A`, `094 PDT 1201A` и `094pdt1201a` считаются одним обозначением.
Если под одно нормализованное обозначение подпадают разные изделия, привязка не
делается — лучше пусто, чем неверно. Строки короче трёх символов игнорируются.

В логе экспорта появляется строка «Из них опознано по надписи на символе: N».

## 3d. Перенос соединений (проводов)

Приборы без проводов — это не схема, поэтому геометрия связей переносится тоже.

**Выгрузка.** При обходе листов для каждого сегмента цепи вызывается
`NetSegment.GetLineSegments`, который отдаёт лист и массивы координат ломаной.
Каждая точка пишется отдельной строкой листа «Соединения»: `№ соединения`,
`№ точки`, `Имя листа`, `ID листа`, `X`, `Y`, `Тип точки`, `Сигнал`, `ID сегмента`.
Точки одного провода объединяет общий `№ соединения`.

**Загрузка.** Строки группируются по `№ соединения` и рисуются одним вызовом
`Connection.Create(лист, число точек, X[], Y[], типы[])` — то есть ломаная
воспроизводится точка в точку, а не заменяется прямой.

Про базу массивов: E3 **возвращает** массивы 1-based (обёртка Zuken срезает нулевой
элемент), а **принимает** 0-based. Поэтому на вход первым пробуется 0-based —
при неверной базе первая точка провода ушла бы в ноль. Дальше идут запасные варианты:
без массива типов, 1-based и, в самом крайнем случае,
`CreateConnectionBetweenPoints` по крайним точкам. Выбранный способ пишется в лог.

Оба метода доступны с давних версий (`GetLineSegments` — с 9.10, `Connection.Create` —
с 8.50), то есть на 2022 SP2 работают.

## 3e. Что означает «координаты не совпали»

`GetSchemaLocation` возвращает `0` не только для неразмещённого символа, но и **для
gate**. Раньше инструмент считал такой символ ошибкой размещения — отсюда были 89
ложных «координаты не совпали» на проекте, где по факту всё встало правильно.

Теперь размещение считается успешным по результату `Place`, а расхождение фиксируется
только если обратное чтение реально вернуло лист и другие координаты. В логе такие
символы помечаются как «позиция не перечитывается (gate)».

## 4. Если координаты всё ещё расходятся

Сигнатуры COM у E3 немного отличаются между сборками, поэтому чтение позиции подбирается
на месте: программа пробует по очереди `GetSchemaLocation(x, y, grid)`,
`GetSchemaLocation(sheet, x, y, grid)`, `GetSchemaLocation(x, y)`, `GetPosition(x, y)` и
берёт первый вариант, который вернул числа. Что выбрано — видно по кнопке **«Методы API»**
и в логе при подключении.

Порядок проверки на реальном проекте:

1. **«Показать координаты символов»** — сырой дамп в двух разделах: **A** по листам
   (`GetSheetIds` → `GetSymbolIds` → символы) и **B** по изделиям
   (`GetAllDeviceIds` → `GetSymbolIds` → символы). Для каждого символа печатаются
   результаты и коды ошибок всех методов: `GetDeviceId`, `GetOwnerDeviceId`, `GetSheetId`,
   `IsPlaced`, три варианта `GetSchemaLocation`, `GetPosition`, `GetArea`, `GetRotation`,
   плюс значение старой формулы. Ничего не скрывается: если символов нет или метод
   отсутствует, это видно в строке с кодом ошибки.
2. **«Тест чтение — запись — чтение»** — сдвигает один символ на +10/+10 мм, проверяет
   результат и возвращает назад. Если тест зелёный, круговой обмен рабочий.
3. **Импорт с галочкой «только проверка»** — прогон без изменений проекта: проверяются
   наличие изделий, листов и корректность координат.

Если в логе появилось «координаты берутся из габарита (GetArea)» — значит ни один прямой
способ чтения не сработал на этой сборке. Сохраните лог кнопкой **«Сохранить лог»** и
пришлите: по выводу диагностики видно, какое имя метода нужно добавить.

## 5. Формат Excel

Лист **«Изделия»** — колонки 1–53 те же, что в прежнем шаблоне (обратная совместимость):

| № | Заголовок | Назначение |
|---|---|---|
| 1 | Поз. обозначение | ключ сопоставления с проектом |
| 2 | ComponentName | компонент библиотеки, нужен при создании |
| 3–53 | `*TAG титула` … `Клемма (2)` | атрибуты изделия |
| 54 | Имя листа | лист размещения |
| 55, 56 | X, Y | координаты точки привязки, мм |
| 57, 58 | Поворот, Зеркало | ориентация символа |
| 59, 60 | ID символа, Имя символа | точная привязка к символу |
| 61 | Символов у изделия | справочно |
| 62, 63 | ID листа, ID изделия | справочно, для разбора |

Лист **«Размещения»** — по строке на каждый размещённый символ: `Поз. обозначение`,
`№ симв.`, `ID символа`, `Имя символа`, `Имя листа`, `ID листа`, `X`, `Y`, `Поворот`,
`Зеркало`, `ID изделия`. Если этот лист есть в файле, импорт размещает по нему, посимвольно;
если нет — по колонкам 54–56 основного листа (первый символ изделия).

Пустая ячейка атрибута означает «не менять». Очистить значение атрибута через таблицу
нельзя — это сделано намеренно, чтобы неполная выгрузка не стирала данные в проекте.

2. Запустить `E3_Devices_Tool.hta`, нажать **«Подключиться»**.
3. Выгрузка: **«Выгрузить изделия»** — файл появится на рабочем столе и сразу подставится

4. Правка координат в Excel.
5. Загрузка: галочки → **«Запустить импорт»**. Первый прогон стоит делать с

6. Галочка «сохранить проект в конце» либо сохранение вручную в E3.

## 6a. Проверка файла после правок

`check_vbscript.py` — статическая проверялка VBScript внутри HTA. Запуск:

```
python3 check_vbscript.py E3_Devices_Tool.hta
```

Ловит то, что иначе всплывает только в runtime и роняет весь скрипт целиком
(тогда любая кнопка выдаёт «Значением свойства "uiConnect" ... не является объектом Function» —
это значит, что блок `<script>` не скомпилировался):

* зарезервированные слова VBScript в именах переменных и параметров
  (`variant`, `type`, `set`, `get`, `stop`, …) — самая коварная ошибка, она валит компиляцию;
* незакрытые `If` / `For` / `Do` / `Select Case` / `With` / `Sub` / `Function`;
* повторный `Dim` одного имени в процедуре;
* `ReDim Preserve` по двумерному массиву (в VBScript расти может только последняя размерность);
* несовпадение числа аргументов в вызове и в объявлении процедуры;
* символы, не кодируемые в windows-1251.

## 7. Ограничения

* Смена `ComponentName` у существующего изделия не выполняется — только сообщение в лог.
* Зеркало читается, но не применяется при импорте: подходящий метод записи в API этой
  сборки не подтверждён. Поворот применяется, если сборка отдаёт `SetRotation`/`SetAngle`.
* Соединения, кабели и жилы не затрагиваются — инструмент работает с изделиями и
  размещением символов.
* Перенос символа на **другой** лист зависит от сборки: если `SetSchemaLocation` не
  принимает идентификатор листа, программа сообщит о несовпадении координат после записи.
* Файл сохранён в кодировке **windows-1251** (как и прежние скрипты) — так mshta
  гарантированно читает русские имена атрибутов. При правке открывайте в редакторе с
  явной кодировкой Windows-1251 (Notepad++: Кодировки → Windows-1251), иначе имена
  атрибутов побьются и перестанут совпадать с базой E3.
