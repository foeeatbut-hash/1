# E3.series ↔ Excel — версия на Python

Инструмент выгружает изделия, координаты символов, провода и параметры листов из
открытого проекта E3.series в книгу Excel и загружает изменения обратно. Порт
HTA-версии (`../E3_Devices_Tool.hta`), логика та же и проверенная, но код разбит
на модули, покрыт тестами и не требует установленного Microsoft Excel.

Каждый объект в книге подписан своим **GID** — постоянным идентификатором,
который E3 выдаёт сама. Поэтому символ без обозначения, без имени и без единого
заполненного атрибута выгружается и возвращается на место так же точно, как
заполненный. Подробности — «Как программа опознаёт объекты» ниже.

Чертёж раскладывается в книге так, как он устроен: изделия отдельно по видам
(`.PREFERRED_VIEW`: 4 — ФСА, 5 — схема соединений), схемная часть и подвал ФСА —
на отдельных вкладках, вид и формат листа — в каждой строке. Поэтому изделия не
повторяются, а загрузка ставит каждый символ ровно туда, откуда он был выгружен,
даже когда в проекте есть листы с одинаковыми именами. Отдельной вкладкой идёт
сверка сигналов DI/DO/AI/AO вида 4 против вида 5. Подробности — в разделе 4.

## 1. Почему Python

Не из-за моды: **Zuken сам публикует обёртку над COM-API E3.series** — пакет
[`e3series`](https://pypi.org/project/e3series/) на PyPI, автор
`e3-support@de.zuken.com`. Внутри ~60 000 строк типизированных методов, и у
каждого в подсказке указана минимальная версия TLB. Это снимает главную боль
предыдущей версии: раньше приходилось перебором выяснять, какой метод есть на
сборке 23.20, а какой появился позже.

Из исходников этой обёртки взяты три соглашения, которые в HTA подбирались
опытным путём:

| Что | Как на самом деле |
|---|---|
| out-параметры | возвращаются в кортеже результата: `ret, ids = job.GetSheetIds(0)` |
| массивы идентификаторов | E3 отдаёт **1-based**, нулевой элемент служебный |
| `Connection.Create` | принимает массивы **тоже 1-based** — обёртка Zuken сама добавляет фиктивный нулевой элемент |

Последнее особенно важно: в HTA вариант «0-based» пробовался первым, и если бы он
случайно «сработал», первая точка каждого провода уехала бы в ноль. Здесь
1-based используется сразу, а 0-based остался запасным.

Что ещё изменилось к лучшему:

| Проблема HTA-версии | Как теперь |
|---|---|
| слово `variant` в имени параметра ломало компиляцию **всего** скрипта | обычная ошибка с номером строки, остальные функции живы |
| файл в cp1251, правки через `iconv`, символ `×` не влезал в кодировку | UTF-8 везде |
| `IsNumeric(Empty) = True` — экспорт молча писал нули | `parse_num` отвергает пустое значение, есть тест |
| Excel через COM: нужен установленный Excel, ячейка за ячейкой | `openpyxl`, Excel не нужен, чтение и запись пачкой |
| нет `DoEvents` → нарезка циклов через `setTimeout` | рабочий поток, кнопка «Стоп» работает сразу |
| 3730 строк в одном файле | модули по 150–400 строк |
| проверить логику можно было только на живом проекте | 53 теста, из них полный круг «проект → Excel → проект» на поддельной E3 |

## 2. Установка

### Обычная (есть Python)

Нужен **Python 3.11+ разрядности x64** — под 64-битную E3.series.

```powershell
cd tools\e3series\python
pip install -r requirements.txt
run.bat
```

Необязательно, но рекомендую поставить обёртку Zuken — она даёт автодополнение по
API E3 в редакторе. Версия подбирается под вашу E3; по таблице Zuken для
**23.20 (2022 SP2) это 26.10.0**:

```powershell
pip install e3series==26.10.0
```

Программа работает и без неё: обращения к COM идут напрямую, обёртка нужна только
как справочник при доработке кода.

### Portable (Python не устанавливается)

```powershell
powershell -ExecutionPolicy Bypass -File make_portable.ps1
```

Скрипт разворачивает embeddable-сборку Python в `runtime\`, ставит туда `openpyxl`
и `pywin32`, копирует DLL `pythoncom`/`pywintypes` рядом с `python.exe` (иначе в
embeddable-сборке они не находятся) и проверяет результат. После этого папку
можно скопировать на флешку и запускать `run.bat` на любом компьютере с E3.

Если на рабочем компьютере нет интернета, скачайте заранее на домашнем:

```powershell
# на компьютере с интернетом
pip download -r requirements.txt -d wheels --platform win_amd64 --python-version 312 --only-binary :all:
# затем на рабочем
powershell -File make_portable.ps1 -PythonZip D:\python-3.12.8-embed-amd64.zip -GetPip D:\get-pip.py -WheelDir D:\wheels
```

## 3. Запуск

### Окно

```
run.bat
```

Порядок работы:

1. **Подключение.** «Найти» перечисляет запущенные экземпляры E3 (по мониторам
   Running Object Table), можно выбрать нужный по PID — в HTA этого не было.
2. **Листы.** Галочки `.PREFERRED_VIEW = 4/5` или «все листы». Программа читает и
   пишет только выбранные виды.
3. **Файл Excel.** «Шаблон» создаёт пустую книгу со всеми столбцами.
4. **Вкладка «Выгрузка в Excel»** — какие листы книги заполнять и как делить
   лист на схему и подвал.
5. **Вкладка «Загрузка в E3»** — что применять к проекту. Первый прогон делайте
   кнопкой «Проверить книгу»: она посчитает, сколько строк пройдёт, ничего не
   меняя.

Всё то же есть в меню, а главные действия — на панели под заголовком.
Горячие клавиши: `F5` — подключиться, `F9` — выгрузить, `F10` — загрузить,
`F11` — развернуть журнал, `Esc` — остановить, `Ctrl+O` — выбрать книгу.

Окно разделено подвижной перегородкой: сверху вкладки настроек, снизу журнал.
Перегородку можно тащить мышью, кнопка «Развернуть» отдаёт журналу всё окно.
Настройки прокручиваются, поэтому на маленьком экране ничего не обрезается.
Внизу — строка состояния с прогрессом. Журнал: подробный режим включён по
умолчанию, текст выделяется и копируется, есть кнопки «Копировать»,
«Сохранить…» и «Очистить».

### Консоль

```powershell
run.bat instances                                     # какие E3 запущены
run.bat export --views 4 --out C:\work\out.xlsx
run.bat export --views all --only-placed --out C:\work\placed.xlsx
run.bat import --file C:\work\out.xlsx --place --connections --dry-run
run.bat import --file C:\work\out.xlsx --place --connections --save
run.bat template --out C:\work\template.xlsx
```

Полный список ключей — `run.bat export --help`.

## 4. Структура книги

Девять листов. Столбцы ищутся **по имени**, поэтому файл, выгруженный старой
HTA-версией (56 столбцов) или прошлой версией этой программы (63 или 67
столбцов), читается без правок, а лишние столбцы не мешают. Новые столбцы всегда
дописываются в конец.

| Вкладка | Что в ней | Применяется обратно |
|---|---|---|
| `Изделия` | всё, что есть в проекте: по строке на объект | да |
| `ФСА (вид 4)` | изделия функциональной схемы с атрибутами | нет, отчёт |
| `Схема соединений (вид 5)` | то же для вида 5 плюс сверка с ФСА | нет, отчёт |
| `Схема` | размещения символов в схемной части | да |
| `Подвал` | размещения символов в подвале ФСА | да |
| `Соединения` | ломаные проводов | да, по галочке |
| `Надписи` | свободные тексты листов | да |
| `Листы` | виды, рамки и габариты листов | да |
| `Сверка сигналов` | DI/DO/AI/AO вида 4 против вида 5 | нет, отчёт |

### Почему листов девять, а не один

Одно изделие на чертеже размещено не один раз:

* на **ФСА** (`.PREFERRED_VIEW = 4`) — в схемной части, над таблицей;
* там же ещё раз — в **подвале**, таблице внизу листа, где приборы перечислены
  построчно;
* на **схеме соединений** (`.PREFERRED_VIEW = 5`) — третий раз.

В реальном проекте это видно прямо в цифрах: на листе «1» 49 размещённых
символов при 36 различных позициях, и 25 из 49 стоят на одной высоте Y = 35 —
это и есть строка подвала. Если сложить всё в одну таблицу, изделия
повторяются и понять, какая строка какому месту чертежа соответствует,
невозможно. Поэтому размещения разведены по вкладкам «Схема» и «Подвал», изделия
разведены по видам, а вид листа пишется в каждую строку.

**Имена листов в проекте повторяются:** у ФСА и схемы соединений одного узла имя
одно и то же (в проекте пользователя 22 листа на 19 имён). Поэтому лист
адресуется парой «имя + вид» либо своим `ID листа`.

### Как программа опознаёт объекты

Опознание больше не держится на «Поз. обозначении». Цепочка при загрузке, по
убыванию надёжности:

| Чем ищем | Когда работает | Откуда берётся |
|---|---|---|
| `GID` | всегда, если книга выгружена из этого же проекта | E3 выдаёт сама, TLB 23.00 |
| `ID символа` / `ID изделия` | в пределах той же сессии проекта | номер объекта |
| `Поз. обозначение` + `№ символа` | если объект пересоздан | атрибут изделия |
| `Символ в базе` + `Версия символа` | объекта в проекте нет — вставляем такой же | `Symbol.Load` |

Почему это важно. Раньше строка без «Поз. обозначения» **молча пропускалась** —
и на загрузке, и (если символ не привязался ни к одному изделию) на выгрузке.
В проекте, где этот атрибут не заполнен, терялась бо́льшая часть чертежа. Теперь
обозначение — вспомогательное поле: строку определяет GID.

Заодно связь «символ → изделие» берётся у E3 напрямую (`Device.SetId`,
получив идентификатор символа, делает текущим изделие-владельца), а не
угадывается по надписям на символе. Догадка осталась последней ступенью.

Символы, у которых изделия нет вовсе — рамки, таблицы, графика, соединители, —
выгружаются наравне с остальными: в строке `Тип объекта` у них написано
«без изделия», а `Поз. обозначение` пусто. Раньше такие символы отбрасывались.

В журнале после загрузки видно, чем именно опознана каждая группа строк:
«Опознано: по GID …, по ID символа …, по обозначению …». Если по GID ноль, а
остальное не ноль — книга выгружена старой версией программы, и точность ниже.

### Как программа находит подвал

Три правила, в порядке убывания главенства:

1. **Ручная граница.** Поле «граница подвала, Y мм» на вкладке выгрузки. Если
   задана — работает только она.
2. **Имя символа в базе E3.** Подвальные символы и компоненты названы
   `Подвал_…`; программа читает `Symbol.GetSymbolTypeName()` и
   `Device.GetComponentName()`. Это прямое указание назначения символа, а не
   догадка о его месте, поэтому оно надёжнее геометрии. Правило взято из
   рабочего скрипта сверки сигналов.
3. **Геометрия.** Там, где таких имён нет: ищется первая снизу пустая полоса
   шире 20 мм в нижних 45 % листа, при условии что выше неё остаётся не меньше
   60 мм содержимого. На реальном проекте граница получается 60–86 мм — ровно по
   верхнему краю штампа.

Имя и геометрию на одном листе программа не смешивает: символ подвала, стоящий
выше найденной границы, попал бы в схему, и изделие задвоилось бы именно там,
где мы этого избегаем. Каким правилом воспользовались, написано в столбце
`Зона определена` — и в строке размещения, и в листе «Листы».

### «Изделия» — одна строка на изделие

| № | Столбец | Смысл |
|---|---|---|
| 1 | `Поз. обозначение` | ключ поиска изделия, он же атрибут E3 |
| 2 | `ComponentName` | компонент библиотеки; без него изделие не создать |
| 3–53 | `*TAG титула` … `Клемма (2)` | атрибуты изделия, пишутся по имени |
| 54 | `Имя листа` | куда поставить символ |
| 55–56 | `X`, `Y` | координаты, мм, начало отсчёта — левый нижний угол листа |
| 57 | `Поворот` | «0», «90», «MX90»; зеркало закодировано здесь же |
| 58 | `Зеркало` | «MX» / «MY» / пусто — то же, что и в «Повороте», но отдельно |
| 59–60 | `ID символа`, `Имя символа` | какой именно символ размещать |
| 61 | `Символов у изделия` | справочно; 0 — размещать нечего |
| 62 | `ID листа` | важнее имени: имена листов в проекте повторяются |
| 63 | `ID изделия` | справочно |
| 64 | `Вид листа` | `.PREFERRED_VIEW`: 4 — ФСА, 5 — схема соединений |
| 65 | `Формат листа` | рамка листа; можно поменять — при загрузке применится |
| 66 | `Зона` | «схема» или «подвал» — где стоит это размещение |
| 67 | `Размещений` | сколько раз изделие размещено всего |
| 68–71 | `!Dev_OpisaniePR_DI/DO/AI/AO` | счётчики сигналов; их складывает сверка |
| 72–74 | `dip_Fnumber`, `dip_F_tag`, `dip_SH_tag` | позиционное обозначение и TAG |
| 75 | `dip_type` | `cable`, `xt`, `jb` в сверке не участвуют |
| 76–80 | `ID Сигнала 1` … `ID Сигнала 5` | идентификаторы сигналов |
| 81 | `GID` | ключ изделия; по нему оно находится без «Поз. обозначения» |

Координаты здесь — **основного** размещения: схемная часть предпочитается
подвалу, дальше по меньшему виду, листу и номеру символа. Выбор строго
определён, поэтому повторная выгрузка того же проекта даёт тот же файл.
Если в книге есть вкладки размещений, при загрузке координаты с листа
«Изделия» не используются — размещение идёт по ним.

### «ФСА (вид 4)» и «Схема соединений (вид 5)» — изделия по видам

Те же столбцы, что и на листе «Изделия», но состав другой: на вкладку попадают
изделия, размещённые на листах этого вида. Изделие с двумя размещениями на ФСА
(в схеме и в подвале) в таблице встречается **один раз** — вкладка отвечает на
вопрос «что есть на этом виде», а не «где что стоит».

Вкладка вида 5 обрабатывается следующим шагом: рядом с каждым изделием идёт
сверка с видом 4.

| Столбец | Смысл |
|---|---|
| `Размещений здесь` | сколько символов изделия стоит на листах вида 5 |
| `Размещений на ФСА` | столько же для вида 4 |
| `Есть на ФСА` | «да» / «нет» |
| `Статус сверки` | «совпадает», «число размещений разное», «нет на ФСА» |

Обе вкладки — **отчёты**: в проект они не применяются. Иначе одно изделие
записывалось бы трижды, а правка на главном листе была бы затёрта неизменённой
копией со вкладки вида. Правку, сделанную по ошибке на отчёте, программа
находит при загрузке и называет поимённо в журнале — молча она не пропадёт.
Если листа «Изделия» в книге нет вовсе, вкладки видов используются вместо него.

### «Схема» и «Подвал» — одна строка на символ

Одинаковый набор столбцов: `GID`, `Поз. обозначение`, `№ символа`, `ID символа`,
`Имя символа`, `Символ в базе`, `Версия символа`, `Имя листа`, `ID листа`,
`Вид листа`, `Формат листа`, `Зона`, `X`, `Y`, `Поворот`, `Зеркало`, `Масштаб`,
`ID изделия`, `Тип объекта`, `Зона определена`.

`GID` — ключ строки, править его не нужно. `Символ в базе` и `Версия символа`
нужны только для загрузки в другой проект: по ним программа вставит такой же
символ, если своего объекта там нет (галочка «вставлять отсутствующие символы»).

Вместе эти две вкладки описывают чертёж полностью: в каждой из них изделие
встречается столько раз, сколько у него символов в этой зоне. При загрузке
читаются обе, сначала «Схема», потом «Подвал» — как и любая другая вкладка с
`№ символа` и координатами, так что свои вкладки тоже сработают.

Как определяется зона — см. «Как программа находит подвал» выше. Найденная
граница и способ выгружаются в лист «Листы», так что видно, чем именно программа
разделила лист. Деление можно выключить — тогда получится одна вкладка
«Размещения», как в прошлой версии.

Зона — только способ разложить строки по вкладкам. Координаты в строках
абсолютные, поэтому строка, перенесённая из «Подвала» в «Схему», встанет туда,
куда указывают её `X` и `Y`.

### «Соединения» — одна строка на точку ломаной

Точки одного провода объединяет `№ соединения`; есть вид и формат листа.
`Тип точки` — то, что вернул `GetLineSegments`. Провода создаются **после**
размещения символов: логическую связь E3 устанавливает сам по факту касания
вывода.

### «Надписи» — одна строка на свободный текст

`ID надписи`, `Имя листа`, `ID листа`, `Вид листа`, `Формат листа`, `Зона`,
`X`, `Y`, `Поворот`, `Высота`, `Тип надписи`, `Текст`.

Сюда попадают **только свободные тексты листа**. `Sheet.GetTextIds` отдаёт заодно
подписи символов, но их переносить нельзя: E3 формирует их сама из атрибутов, и
записанное поверх значение она же и затрёт. Поэтому из списка листа вычитается
всё, что вернул `Symbol.GetTextIds` каждого символа на нём.

При загрузке (галочка «переносить надписи», включена) надпись адресуется своим
`ID надписи`; программа применяет новый текст и новые координаты. Перед записью
проверяется, что надпись с этим ID и правда лежит на том листе, который указан в
строке: при загрузке книги в другой проект тот же ID окажется у совсем другого
текста, и молча его переписать было бы хуже всего — такая строка пропускается с
сообщением в журнале. Строки без `ID надписи` создают новую надпись, но только
по отдельной галочке «создавать отсутствующие надписи» (выключена).

### «Сверка сигналов» — отчёт

Перенос рабочего VBScript-скрипта сверки внутрь программы: отчёт получается
прямо при выгрузке, той же книгой, и без второго обхода E3 — размещения уже
собраны. Правила взяты дословно:

* **вид 4 считается только по подвалу.** На ФСА изделие нарисовано дважды, а
  перечнем сигналов является именно подвал;
* **вид 5 считается целиком** — там дублей нет;
* **исключения по `dip_type`**: `cable`, `xt`, `jb`. Кабели, клеммники и коробки
  сигналов не несут, но стоят на обоих видах и портили бы итог;
* **изделие считается один раз на лист**, но суммируется по листам: изделие,
  встреченное на двух листах, даёт двойной вклад — по этому признаку в отчёте
  видно продублированное изделие.

Блоки отчёта: сводка по листам вида 4, то же по виду 5, сводная таблица DI/DO/AI/AO
с разницей и статусом, расхождения по TAG (`dip_F_tag`), расхождения по
внутреннему ID изделия, таблица сигналов. Сверка идёт двумя способами не для
красоты: TAG ловит переименования и опечатки, внутренний ID — случаи, когда один
и тот же объект проекта попал не на тот вид.

### «Листы» — одна строка на лист

`ID листа`, `Имя листа`, `Вид листа`, `Назначение вида`, `Формат листа`,
`Символов на листе`, габарит (`X мин` … `Y макс`), `Граница подвала Y`,
`Зона определена`.

Что программа делает с этим листом при загрузке:

| Столбец | Действие | Галочка |
|---|---|---|
| `Формат листа` | `Sheet.SetFormat` — меняет рамку листа | «применять формат листа из Excel», включена |
| `Вид листа` | пишет `.PREFERRED_VIEW` | «менять вид листа», выключена |
| строки без такого листа | `Sheet.Create` с указанной рамкой | «создавать отсутствующие листы», выключена |

Формат листа берётся и из строк элементов: поправить `Формат листа` можно прямо
в строке изделия. Лист «Листы» при расхождении главнее, о противоречиях внутри
одной таблицы программа предупреждает и берёт первое значение.

Смена вида выключена по умолчанию не из осторожности ради осторожности:
`.PREFERRED_VIEW` переопределяет назначение всего листа, и, поменяв его, вы
меняете и то, какие изделия программа считает «своими» на этом листе.

## 5. Что можно и чего нельзя на 23.20

Можно: читать и писать атрибуты, создавать изделия из компонентов, ставить и
переносить символы, читать и создавать провода, читать, переносить и создавать
надписи, фильтровать по видам листов, менять формат (рамку) листа и его
`.PREFERRED_VIEW`, создавать листы.

Методы, на которых это держится, и с какой версии библиотеки типов они есть
(проверено по официальной обёртке Zuken, у нас TLB 23.20):

| Метод | Что делает | Есть с |
|---|---|---|
| `Sheet.GetFormat` / `SetFormat` | читает и меняет рамку листа | 8.50 |
| `Sheet.GetDrawingArea` / `GetWorkingArea` | габарит листа — по нему ищется подвал | 8.50 |
| `Sheet.Create` | создаёт лист с заданной рамкой | 8.50 |
| `Sheet.Get/SetAttributeValue` | `.PREFERRED_VIEW` | 8.50 |
| `Symbol.GetSymbolType` | тип символа (рамка, таблица, обычный) | 20.00 |
| `Symbol.GetSymbolTypeName` | имя типа символа — по нему опознаётся подвал | 8.50 |
| `GetGID` / `SetGID` | постоянный идентификатор объекта; `SetGID` ищет, а не присваивает | 23.00 |
| `Device.SetId(символ)` | обратная связь «символ → изделие» | 8.50 |
| `Symbol.Load` | взять символ из базы по имени — вставить такой же | 8.50 |
| `Symbol.GetScaling` / `SetScaling` | масштаб символа | 8.50 |
| `Sheet.GetTextIds` | надписи листа | 8.50 |
| `Text.GetSchemaLocation` / `SetSchemaLocation` | положение надписи | 9.10 |
| `Text.GetText` / `SetText` | содержимое надписи | 8.50 / 9.10 |
| `Graph.CreateText` / `CreateRotatedText` | создать надпись на листе | 9.10 |

Нельзя (это ограничение API, а не программы):

* **заменить компонент** у существующего изделия — программа сообщает о
  расхождении в журнале, но подменить не может;
* **переименовать** обозначение изделия;
* **удалить с перекоммутацией**.

Всё это делает `ProjectConfigurator`, он появился в TLB 26.00 — это E3.series
2025. На 23.20 его нет.

Ещё три вещи, которые видны в журнале и не являются дефектами:

* **изделия без символов.** У компонента нет схемного символа — ставить нечего.
  В конце импорта выводится список таких компонентов с количеством.
* **строки без `ComponentName`.** Создать изделие не из чего; считаются отдельно.
* **gate.** `GetSchemaLocation` возвращает 0 вместо листа не только для
  неразмещённого символа, но и для gate. Поэтому успех записи определяется
  результатом `Place`, а «координаты не совпали» сообщается только если позиция
  реально прочиталась и отличается. В HTA это давало 89 ложных тревог.

## 6. Где что менять

```
e3tool/
  columns.py   схема столбцов книги — добавить атрибут проще всего здесь
  util.py      разбор чисел, нормализация обозначений, строки таблиц
  e3api.py     всё общение с COM: перечисления, координаты, Place, провода
  project.py   кэш проекта и листов, поиск изделия и листа, граница подвала
  excel_io.py  чтение и запись .xlsx, оформление листов
  export.py    выгрузка: три прохода (объекты -> листы -> атрибуты), зоны, вкладки
  signals.py   сверка сигналов DI/DO/AI/AO: перенос рабочего VBScript-скрипта
  importer.py  загрузка: листы -> изделия -> размещения -> надписи -> провода
  worker.py    рабочий поток, единолично владеющий соединением с E3
  ui.py        окно на tkinter: меню, панель, вкладки настроек, журнал в панели
  cli.py       консольный режим
tests/
  fake_e3.py        поддельная E3 с теми же соглашениями, что у настоящей
  test_logic.py     разбор данных, схема столбцов, Excel
  test_roundtrip.py экспорт и импорт целиком, включая полный круг через файл
```

Правило одно: **в `export.py` и `importer.py` не должно быть обращений к COM
напрямую** — только через `e3api`. Тогда логика остаётся проверяемой на поддельной
E3, без Windows.

Добавить свой атрибут в выгрузку: одна строка в `ATTRIBUTE_HEADERS`
(`columns.py`). Он появится и в шаблоне, и в выгрузке, и будет записываться при
импорте.

Имена атрибутов сверки (`!Dev_OpisaniePR_DI`, `dip_F_tag`, `dip_type` и прочие)
собраны в `columns.py` рядом с `SIGNAL_HEADERS`. Менять их нельзя произвольно:
по ним отчёт находит данные в проекте.

Признак подвала — константа `FOOTER_MARKER = "подвал_"` в `columns.py`.

## 7. Как программа отпускает E3

Скрипт, работающий через COM, держит проект в **открытой транзакции**: пока она не
закрыта, E3 считает себя занятой, и работать в ней нельзя — даже после того, как
скрипт закрыли. Поэтому после каждой выгрузки и загрузки программа делает это:

| Шаг | Метод E3 | Зачем |
|---|---|---|
| перед работой | `SetEnableInteractiveDialogs(False)` | если E3 покажет модальное окно, встанут обе программы: она ждёт ответа, мы ждём её |
| перед записью | `UndoAfterExecution(False)` | явно запрещаем откат сделанного по завершении скрипта |
| в процессе | `Application.Sleep(1)` каждые 20 строк | E3 успевает разобрать свою очередь и не выглядит мёртвой |
| после работы | **`Job.FinalizeTransaction()`** | закрывает транзакцию — это и есть снятие «занятости» |
| после работы | `SetEnableInteractiveDialogs(True)` | возвращаем диалоги, иначе E3 останется «немой» |
| после работы | освобождение объектов COM | галочка «отпускать E3 после операции» |

Закрытие транзакции и возврат диалогов выполняются **и после ошибки тоже** — иначе
неудачная загрузка оставила бы проект занятым.

Галочка «**отпускать E3 после операции**» (включена) освобождает объекты COM и
обнуляет соединение. К следующей операции программа подключится сама — в журнале
будет строка «Переподключаюсь к E3 (PID …)». Кнопка «**Отпустить**» делает то же
самое немедленно.

Если после большой загрузки E3 всё равно подтормаживает, дело в её истории отмены:
227 созданных изделий — это тяжёлый undo-буфер. Галочка «**очистить историю отмены
E3 после загрузки**» вызывает `Job.RemoveUndoInformation()`. По умолчанию она
выключена: очистка необратима, отменить импорт средствами E3 после неё не выйдет.

## 8. Журнал

Журнал пишется **сразу в файл**, а не только на экран: папка `logs\` рядом с
программой, имя `E3_Tool_log_ГГГГММДД_ЧЧММСС.txt`. Путь виден внизу окна, кнопка
«Открыть папку» ведёт туда же. Если программа упадёт, файл всё равно останется.

Подробный режим включён по умолчанию. Что видно в журнале:

* окружение: версия Python и его разрядность, версии pywin32 и openpyxl;
* версия E3 и имя проекта;
* **почему каждый лист попал или не попал в выборку** — значение `.PREFERRED_VIEW`
  по каждому листу и сводка «виды листов в проекте — 1: 19, 4: 3»;
* три фазы выгрузки с числами и временем каждой;
* по каждому листу: сколько символов, сколько привязано к изделиям, сколько
  сегментов проводов;
* сколько изделий вышло с координатами и сколько без;
* какие сигнатуры COM приняла ваша сборка E3;
* отказавшие вызовы COM — по одной строке на метод, с кодом HRESULT и пояснением
  от E3.

Ошибка печатается разобранной: тип, сообщение, код COM с расшифровкой, файл,
номер строки и сам текст этой строки. Гадать по трассе не нужно — сразу видно,
где сломалось.

Текст журнала можно выделять мышью и копировать: работают Ctrl+C, Ctrl+A и правая
кнопка мыши. Кнопка «**Копировать всё**» кладёт журнал в буфер целиком, «**Сохранить
как TXT…**» спрашивает путь и пишет файл, «**Открыть папку**» ведёт к автоматическому
журналу. Прокрутка не дёргается вниз, пока вы читаете что-то выше.

## 9. Если что-то не работает

**«'_contextvars.Context' object is not callable» при выгрузке** — исправлено в
версии 1.1.0. Причина была в том, что класс `Worker` наследовался от
`threading.Thread`: у Thread есть служебный `_stop`, а начиная с Python 3.14 ещё
и `_context`, и одноимённые атрибуты подкласса их перекрывали. Теперь Worker
держит поток внутри себя, а не наследуется от него, и есть тест, который следит
за тем, чтобы имена не пересекались.

**E3 занята, в ней нельзя работать после загрузки** — исправлено в версии 1.2.0,
см. раздел 7. Если поведение вернулось, найдите в журнале строку «E3: транзакция
закрыта (FinalizeTransaction)»: без неё проект остаётся занятым.

**«E3 не возвращает out-параметры»** — соединение получилось нетипизированным,
все перечисления будут пустыми. Причины: не зарегистрирована библиотека типов E3
либо Python другой разрядности. Проверьте, что Python x64, и запустите один раз
от имени администратора, чтобы pywin32 собрал кэш типов.

**«Не найден пакет pywin32»** — `pip install pywin32`. В portable-сборке DLL
`pythoncom*.dll` и `pywintypes*.dll` должны лежать рядом с `python.exe`;
`make_portable.ps1` копирует их сам.

**Ничего не найдено в проекте** — проверьте, что в E3 действительно открыт проект
и что галочки вида листов соответствуют вашим листам. Вид листа виден в атрибуте
`.PREFERRED_VIEW`; если не уверены — включите «все листы».

**Символы не привязались к изделиям** — владелец берётся у E3 напрямую
(`Device.SetId` с идентификатором символа), затем идёт опознание по надписи.
Мягкое опознание (по атрибутам `*TAG изделия короткий/полный`) можно отключить
галочкой «опознавать символы по надписям», если оно даёт ложные совпадения.
Символ, у которого изделия нет вовсе, это не ошибка: он выгружается со своим GID
и возвращается на место без всякого изделия.

**Строка не перенеслась, хотя координаты в ней есть** — посмотрите в журнале
строку «Опознано: по GID …». Если по GID ноль, книга выгружена версией до 1.5.0:
в ней столбца `GID` нет, и опознание идёт по «Поз. обозначению», которое может
быть пустым. Выгрузите проект заново.

**Символ не найден при загрузке в другой проект** — это ожидаемо: GID и номера
объектов у каждого проекта свои. Включите «вставлять отсутствующие символы из
базы»: программа возьмёт символ по столбцу `Символ в базе`. Если и там пусто,
вставлять нечего — об этом сказано в журнале поимённо.

**Граница подвала прошла не там** — сначала посмотрите столбец `Зона определена`.
Если там «по имени символа», геометрия не при чём: символ отнесён к подвалу
потому, что его тип в базе называется `Подвал_…`. Если «по геометрии» — в журнале
есть строка «подвал ниже Y=…, пустая полоса … мм между Y=… и Y=…»; когда полосы
на листе нет или она узкая, задайте границу руками полем «граница подвала, Y мм».
Ручная граница главнее обоих правил и действует на все листы.

**Изделия нет в сверке сигналов** — три возможные причины, все видны в отчёте и
журнале: у него `dip_type` из `cable` / `xt` / `jb` (исключено намеренно); на
ФСА оно стоит только в схемной части, без подвальной строки — вид 4 считается
по подвалу; либо у него пустые `!Dev_OpisaniePR_*`, и вклад равен нулю.

**Сверка показывает двойные числа** — изделие считается один раз на лист, но
суммируется по листам. Двойной DI означает, что изделие встречено на двух листах
одного вида; какие это листы, написано в столбцах «Листы вида 4» и «Листы вида 5».

**Надпись не перенеслась** — в журнале будет «надпись … лежит не на том листе».
Так и задумано: книга загружается в другой проект, где тот же `ID надписи`
принадлежит другому тексту. Уберите столбец `ID надписи` и включите «создавать
отсутствующие надписи», если надпись нужно создать заново.

**Правка на вкладке «ФСА (вид 4)» не применилась** — эти вкладки отчёты, в проект
они не пишутся. Программа находит такие правки при загрузке и перечисляет их в
журнале; перенесите их на лист «Изделия».

**Изделие ушло не на тот лист из двух одноимённых** — в строке должен быть
заполнен `Вид листа` (4 или 5) или `ID листа`. По одному имени такие листы
неразличимы: программа возьмёт первый подходящий и напишет об этом в журнал.

**Формат листа не применился** — рамка с таким именем должна быть в библиотеке E3:
`SetFormat` для неизвестного имени отказывает, и в журнале появляется
предупреждение с этим именем. Проверьте написание — оно должно быть точно таким,
как выгрузила программа.

Логика HTA-версии перенесена полностью. Следующий шаг, который стоит обсудить, —

`Job.ImportDrawingForProjectGeneration(..., substitutes, ...)` (доступен с TLB
20.00, то есть на 23.20 есть). Он воспроизводит типовой узел целиком — с
графикой, символами и проводами — подставляя значения вместо заглушек
(`%TAG%`, `%POS%`, `%MODEL%`). Excel в этой схеме становится таблицей подстановок,
и перечерчивать типовые узлы не придётся вообще.
